## Context

`CCRCalendarController` (`app/Http/Controllers/CCRCalendarController.php`) backs the legacy jQuery/Blade Recruiting CCR Calendar (`ccr/calendar` routes). Today `getWeekEvents()` and `fetchScheduleDetailsOfCCR()` hardcode `mssql_facilities.State = 'TX'` and `assigned_ccr = 537`, and pull `type_id IN (2, 996)` (CCR appointments plus block-time entries) with no filter UI at all.

A parallel, actively-maintained feature — the "Patient Review Calls" bucket on the Clinical Care Manager dashboard (`App\Helpers\ClinicalCaseManager::getClinicalCase()`, view `resources/views/ccr/ccmdashboard.blade.php`) — already implements State, Branch, and Clinical-Care-Manager-assignee filters via the shared `components/datatable-filters.blade.php` component and `CommonDatatableFilters`/`ConstantHelper` filter sources, plus a Training/Coverage shift-type distinction derived from `recruiting_schedule.coverage_id` (non-zero = Coverage, else Training). That bucket's "Me Mode" checkbox defaults every user to their own `ccm_id`/`assigned_ccr` records, checked by default regardless of role.

This design reuses that filter-bar/query pattern for the calendar, but does not reuse "Me Mode" verbatim: the ticket needs role-gated defaulting (only Clinical Care Manager and Clinical Quality Nurse get auto-selected as themselves) and an empty-calendar-until-any-filter-is-set behavior, both of which are new logic not present in the dashboard bucket today.

## Goals / Non-Goals

**Goals:**
- Replace the calendar's hardcoded State/Assignee scope with user-driven State, Branch, and Assignee filters, reusing existing filter-bar UI and data-source helpers wherever the shape matches.
- Scope the calendar to Training-shift PRCs only (`coverage_id` null/0), leaving Coverage-shift PRCs for a separate, future PRC Coverage calendar.
- Auto-default the Assignee filter to "self" for Clinical Care Manager and Clinical Quality Nurse roles; leave it empty for everyone else.
- Show no calendar records until at least one filter (State, Branch, or Assignee) has a value.
- Update the calendar title to reflect the selected State.
- Hide (not remove) the block-time "+" button and its trigger; leave the underlying block-time code/routes/views untouched and unused.

**Non-Goals:**
- Renaming CCR/PEPR terminology to PRC — already delivered by the archived `rename-ccr-pepr-to-prc` change / `prc-terminology` spec.
- Building a KanTime-driven state sync. "States synchronized from KanTime" in the ticket is satisfied by reusing the existing static state list (`config('constant.dashboard_state')` via `CommonDatatableFilters::getFilterDataSource('state')`) — the same source every other CCR/PRC filter already uses. No new sync is being built.
- A Coverage-shift calendar (tracked as a separate future ticket).
- Deleting the block-time controller methods, routes, or Blade partials — they are hidden from the UI only, per explicit product direction.
- Feature-flagging this change — ships unconditionally.

## Decisions

**Reuse `CommonDatatableFilters`/`ConstantHelper` data sources, but render as plain `<select>`s placed in the calendar's own left column — not the `components/datatable-filters.blade.php` bar.**
Initial implementation rendered filters via the shared dashboard-bucket filter-bar component (a full-width horizontal bar above the calendar). Per explicit product feedback, this was revised: every sibling calendar in this codebase (`intake`, `ipea`, `trachventclass`, `afterhours`) places its filter dropdowns as plain `<select class="form-control">` elements stacked in the existing `col-md-2 pull-left` column, above the search box — not as a separate full-width bar. The calendar's filters now follow that placement/markup convention instead, while still reusing the same underlying data sources (`CommonDatatableFilters::getFilterDataSource('state')`, `getstatebranch` AJAX endpoint, `ConstantHelper::getClinicalCareManagerAndQualityNurse()`). Assignee search went through two iterations. First, bootstrap-multiselect in single-select mode (no `multiple` attr) was tried, mirroring an existing precedent at `resources/views/user/form.blade.php` (`#role`). This produced inconsistent sizing (correct width before JS init, then the plugin's `<span class="multiselect-native-select"><div class="btn-group">` injected markup wouldn't reliably fill the flex-row width) and popup centering glitches on open — not worth chasing further given the plugin's own layout behavior was the root cause. Final approach: a plain `<input type="text" class="form-control">` backed by a native HTML5 `<datalist>` of assignee names, plus a hidden input holding the resolved user id. This is visually identical in weight/behavior to the plain State/Branch `<select>`s and the existing Search box on the same page (all are just `form-control` inputs), has zero plugin/popup behavior to fight, and still gives type-ahead search via the browser's native datalist matching. On `change` (blur/enter), JS resolves the typed text against the datalist's `data-id` attributes to the numeric id sent to the backend; non-matching text is cleared rather than silently kept.

**New merged assignee source covering Clinical Care Manager + Clinical Quality Nurse — lives in `UserReadRepository`, not `ConstantHelper`.**
`ConstantHelper::getClinicalCareManager()` only queries `roles.name = 'Clinical Care Manager'`, and the ticket's Assignee field must search/select users who could hold either role. An initial implementation added `ConstantHelper::getClinicalCareManagerAndQualityNurse()`/`userHasClinicalCareManagerOrQualityNurseRole()` there, matching that method's own join-based style. Per follow-up feedback (`ConstantHelper` is already oversized and shouldn't keep growing), this was moved to `App\Repositories\User\UserReadRepository` as `getActiveByRoles(array $roleIds): Collection` and `userHasAnyRole(int $userId, array $roleIds): bool`, reusing the `User::roles()` `BelongsToMany` relation (`users_has_roles`) via `whereHas('roles', ...)` — the same idiom already used by `User::getCoverageCoordinators()` and `UserReadRepository::getByRoleAndFacility()` elsewhere in the "not legacy" part of the codebase, keyed by `RolesEnum::CLINICAL_CARE_MANAGER`/`::CLINICAL_QUALITY_NURSE` rather than role-name strings. `CCRCalendarController` injects `UserReadRepository` (alongside `CCRCalendarReadRepository`) and maps the returned `User` models to the `{value, text}` shape the Blade filter markup expects. Alternative considered: two separate Assignee dropdowns (one per role) — rejected, ticket explicitly asks for a single searchable field.

**Assignee matching and display now both reuse the bucket's single-value resolution CASE (a `users` join), not an independent OR across two columns.**
`ClinicalCaseManager::getClinicalCase()` has two separate things that are easy to conflate: (1) a `users` join with a `CASE WHEN assigned_ccr <> '' THEN assigned_ccr WHEN recruiting_schedule.ccm_id ... ELSE mssql_patients.ccm_id END` fallback (behind the `assign_ccm_to_coverage_tracker` flag), used to compute the **displayed** CCM name column; and (2) that bucket's own Assignee/CCM filter WHERE clause, which instead does an independent OR across `mssql_patients.ccm_id` and `mssql_recruitertracker.assigned_ccr` with no fallback priority.

An initial implementation of this calendar copied (2), reasoning that a display name wasn't needed here. Per follow-up feedback this was wrong on two counts: first, a CCM badge *is* needed on each event so the responsible person stays visible when filtering by State/Branch alone (see the "Assignee badge" decision below); second, and more importantly, the product wants exactly one assignee per PRC, not "matches if it touches this user via either column" — a record with `assigned_ccr = User A` and client `ccm_id = User B` should belong to A, not to both A and B. Decision: reuse (1) instead — join `users` via the same priority-ordered CASE (respecting the `assign_ccm_to_coverage_tracker` flag) used for the bucket's display column, then both filter (`whereIn('users.id', $assignee)`) and display (`users.name`) off that single resolved value. Alternative considered: keep the OR-based filter from (2) for filtering while separately computing (1) only for display — rejected, since filter and badge would then disagree about "who this PRC belongs to" whenever the two columns point to different people, which is exactly the confusing case being fixed.

**Assignee badge on calendar events.**
Filtering by State or Branch alone previously gave no way to tell who each PRC was assigned to. Decision: select `users.name as ccm_name` off the same resolved-assignee join described above, and render it as a small badge (`badge badge-info`, matching this app's existing Bootstrap 4 badge convention) on each event card in `weekEvents.blade.php`. No badge is shown when the resolution yields no match (record has neither `assigned_ccr` nor a resolvable `ccm_id`) — deliberately not copying the bucket's `IFNULL(..., 'Unassigned')` display variant, since that's a property of the bucket's dedicated CCM column, not something this new badge needs to replicate.

**Role-gated auto-default is new, purpose-built logic — not a reuse of "Me Mode."**
"Me Mode" is a checkbox, checked by default for every user regardless of role, filtering to `Auth::user()->id`. The ticket wants the opposite default for non-CCM/CQN users (empty, not "everything"). Decision: on calendar load, check `Auth::user()`'s role (via the same `roles`/`users_has_roles` join pattern used by `getClinicalCareManager()`) against `{'Clinical Care Manager', 'Clinical Quality Nurse'}`; if matched, pre-populate and auto-submit the Assignee filter with that user's id, which then flows through the same resolved-assignee matching described above; otherwise leave all filters unset and render an empty calendar.

**Empty-filter state shows a guidance message instead of a blank grid — mirroring the IPEA calendar's existing pattern.**
Per follow-up feedback, an empty result set (no State and no Assignee set) shouldn't just silently render an empty weekly grid — the user should be told why nothing is showing and what to do. `resources/views/ipea/calendar.blade.php` already has exactly this pattern for its own State-only gate: a static `<h3 class="map-intro-text">Select a state from the drop down box to the left</h3>` placeholder sits inside `#weekEvents` and is only overwritten by the AJAX-loaded grid once the required filter is set; the gating decision lives in client-side JS, not the controller. Decision: replicate this — the calendar's `getWeekEvents()` JS function now checks `#prcstate`/`#prcassignee` before firing the AJAX call at all; if neither is set, it swaps `#weekEvents`' contents for the same `map-intro-text` message (text adjusted to "Select a State or Assignee...") instead of hitting the endpoint. Branch is intentionally excluded from this client-side check since it cannot have a value without State also being set (Branch options only populate after a State is chosen), so "State OR Assignee" is equivalent to "State OR Branch OR Assignee" in practice. The server-side short-circuit (task 4.4) is kept as a defense-in-depth backstop in case the endpoint is ever hit directly with all filters empty.

**Empty-calendar-until-any-filter-applied, filters combine with AND.**
Per direct product clarification: State, Branch, and Assignee are independent filters (not mutually required), but if none are set, no records should render — showing all Training PRCs across all states/assignees at once would be overwhelming. This is a deliberate inversion of the dashboard bucket's default (which always shows the current user's records via "Me Mode"). Implementation: short-circuit the query to return no rows when the incoming filter payload is entirely empty, rather than falling through to the bucket's base WHERE-only query.

**Shift-type scoping is a fixed server-side condition, not a user-facing filter.**
Unlike the dashboard bucket (which exposes a Coverage/Training multiselect), this calendar only ever shows Training-shift PRCs — hardcode the existing `CASE WHEN ifnull(recruiting_schedule.coverage_id,0) != 0 THEN 'Coverage' ELSE 'Training' END = 'Training'` condition into the base query rather than exposing another dropdown, per the ticket's explicit scope.

**Hide, don't delete, the block-time button and code.**
Per explicit product direction, remove the "+" anchor's visibility (e.g. wrap in a hidden/removed markup block) but leave `addEvent`/`saveEvent` controller methods, their routes, and `ccr/addEvent.blade.php` in place. Reduces risk/scope versus a full removal, and avoids touching the `type_id == 996` branches embedded in `getWeekEvents()`/`weekEvents.blade.php` that would otherwise need matching cleanup.

**Query logic extracted into `App\Repositories\CCRCalendar\CCRCalendarReadRepository`.**
Per code review feedback, the two large query-building blocks in `CCRCalendarController` (`getWeekEvents()`/`fetchScheduleDetailsOfCCR()`) were moved into a new read repository, following this codebase's existing convention (`app/Repositories/<Domain>/<Domain>ReadRepository.php`, e.g. `MssqlRecruiterTrackerReadRepository`, `TrachVentClassController`'s injected repositories) — constructor-promoted, no interface, resolved automatically by Laravel's container. `CCRCalendarReadRepository::getWeekEvents()` and `::getScheduleDetailsForDate()` take primitive filter values (`state`/`branch`/`assignee` strings/array) and return an `Illuminate\Support\Collection`; the shared assignee-join and State/Branch WHERE logic is factored into private `joinResolvedAssignee()`/`applyFilters()` methods so the two public methods can't drift apart. The controller now only orchestrates: parse request, call the repository, group results into the week-grid's `$scheduleData` structure, render the view.

## Risks / Trade-offs

- [Leaving block-time code live but hidden] → No user-facing risk since the trigger is gone, but it's dead code that could bit-rot or be miswired if `getWeekEvents()`'s query changes; flagged in code comments/PR description so a future cleanup ticket can find it.
- [No KanTime state sync built] → If the ticket's original premise (states actively synced from KanTime) becomes a real requirement later, the state list will need a follow-up migration from static config to a synced table; out of scope here per product direction, but worth revisiting if states become dynamic in KanTime.
- [Assignee auto-default role check duplicates the `getClinicalCareManager()`-style role join] → Two near-identical role-join queries (one for the dropdown source, one for the current-user role check) risk drifting out of sync if role names change; mitigate by having both read from one shared helper/constant for the role name list.
- [Assignee filter/badge reimplemented as a plain `assigned_ccr` check, dropping the `ccm_id` fallback] → Would cause PRCs resolvable only via `ccm_id` to be invisible on the calendar (and unbadged) while still showing correctly in the dashboard bucket, breaking AC7–AC10 silently; mitigate by copying the exact CASE-fallback join from `ClinicalCaseManager::getClinicalCase()` (the one used for its display column) rather than re-deriving it, and covering it with a manual check comparing calendar results/badges against the bucket for the same user.
- [AC9/AC10 ambiguity resolved via direct clarification, not written into the ticket] → The "empty until any filter is applied" rule is broader than the ticket's literal Assignee-specific wording; documented here and in the spec so a future reader understands this is an intentional, confirmed interpretation, not an oversight.

## Migration Plan

No data migration. Deploy is a standard code release: controller/view changes only, no schema changes, no feature flag, no backward-compatibility shim needed since the calendar's current hardcoded behavior (TX/user 537) was not a documented or reliable feature. Rollback is a standard revert of the same commits/PR.

## Open Questions

- Should the merged Clinical Care Manager + Clinical Quality Nurse assignee source also include other roles that might reasonably be assigned a PRC (e.g. Recruiter), or is the Assignee field's searchable population meant to be exactly these two roles? Current assumption: population includes at least these two roles' users; broadening it is low-risk to revisit later since it only affects dropdown search results, not filtering logic.
- Confirm whether `weekEvents.blade.php`'s multi-record-per-slot rendering already handles multiple Training PRCs cleanly today (design assumes yes, since block-time and CCR entries already coexist in the same grid cell) — to be verified during implementation rather than redesigned.
