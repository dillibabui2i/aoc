## Context

`CCRCalendarController`/`CCRCalendarReadRepository`/`resources/views/ccr/{calendar,weekEvents,eventDetails}.blade.php` implement the "PRC Calendar – Recruiting" calendar (State/Branch/Assignee filters, Training-shift-only scope, role-based Assignee default, empty-until-filtered gating). This ticket adds a sibling calendar for Coverage-shift PRCs, with an explicit acceptance criterion (AC16) that the two calendars must behave identically except for shift type — any implementation that risks the two drifting apart over time works against that requirement.

Coverage-shift `recruiting_schedule` rows have `tracker_id = NULL` (there is no Recruiter Tracker involved — coordinators create these directly off a Coverage Tracker shift, per earlier CCR/PRC process changes), and instead carry `coverage_id` pointing at a `coverage_tracker` row. The existing Recruiting-only repository's `mssql_patients` join goes through `mssql_recruitertracker.aoc_patient_id`, which is null for Coverage rows — this must be fixed for Coverage to work at all. `App\Helpers\ClinicalCaseManager::getClinicalCase()` (backs the Clinical Care Manager dashboard's Patient Review Calls bucket, which already lists both shift types together) has already solved this: it joins `mssql_patients` directly via `recruiting_schedule.aoc_patient_id` (a column that exists directly on `recruiting_schedule`), and falls back to `coverage_tracker.new_clinician_name` for the display name when there's no candidate/provider on a coverage row.

## Goals / Non-Goals

**Goals:**
- Ship a fully independent "PRC Calendar – Coverage" calendar (own route, permission, nav entry) restricted to Coverage-shift PRCs (`recruiting_schedule.coverage_id` non-zero).
- Share the query/role logic between both calendars via one generalized repository, so the two calendars cannot silently diverge in filtering/matching behavior.
- Fix the patient-join/candidate-display gap that would otherwise leave Coverage events blank, converging both calendars on the already-proven `ClinicalCaseManager::getClinicalCase()` join pattern.
- Preserve the event-details modal (click-to-view) for Coverage events, without duplicating the whole modal.

**Non-Goals:**
- No time-blocking ("+") button or functionality for the new calendar — it's net new, so there is no legacy behavior to preserve-but-hide (unlike Recruiting, which hid but kept its dead block-time code).
- No changes to `prc-calendar-filters`' documented requirements (Recruiting calendar's behavior is unchanged from the user's perspective; only its shared implementation is refactored).
- No feature flag.

## Decisions

**Generalize `CCRCalendarReadRepository` with a `PrcShiftType` parameter, rather than duplicating a second repository.**
A plain (non-backed) `App\Enums\PrcShiftType { Training, Coverage }` enum parameterizes `getWeekEvents()`/`getScheduleDetailsForDate()`. Both calendars' controllers call the exact same repository methods, differing only in which `PrcShiftType` they pass. Alternative considered: a fully separate `CCRCoverageCalendarReadRepository` copy — rejected per explicit direction, since AC16 requires identical behavior except shift type, and a second copy is a standing invitation for the two to drift apart as either gets modified later.

**Filter parameters consolidated into `App\DTO\PrcCalendarFilterDTO`, per code review.**
Both repository methods originally took `PrcShiftType $shiftType, string $state, string $branch, array $assignee` as four separate positional parameters (on top of the date-range argument each method already has). Per review feedback, these four were consolidated into a single readonly DTO (`app/DTO/PrcCalendarFilterDTO.php`), matching this codebase's existing DTO convention (e.g. `app/DTO/NthInquiryFilterDTO.php` — plain class, `public readonly` constructor-promoted properties, no interface). `applyFilters()` now reads `$filter->state`/`$filter->branch`/`$filter->assignee` directly off the DTO instead of three loose parameters. Both controllers construct `new PrcCalendarFilterDTO($shiftType, $state, $branch, $assignee)` at their call sites. This is a pure signature/readability refactor — no behavior change.

**Fix the `mssql_patients` join and `candidate` display field in the shared repository, benefiting both calendars.**
Changed the join from `mssql_recruitertracker.aoc_patient_id` to `recruiting_schedule.aoc_patient_id` (the column that exists directly on `recruiting_schedule`), and replaced the plain `mssql_recruitertracker.Candidate as candidate` select with the same fallback `CASE` `ClinicalCaseManager::getClinicalCase()` uses: coverage rows (no provider/candidate id, `coverage_id` set) → `coverage_tracker.new_clinician_name`; else if `aoc_provider_id` set → `mssql_providers.fullName`; else → `mssql_recruitertracker.Candidate`. This is required for Coverage rows to display at all, and is a pure convergence-with-proven-logic change for Training rows (the two join paths should already agree for Training rows in practice, since a Training PRC always has a tracker and that tracker's own `aoc_patient_id` should match the schedule row's).

**Assignee resolution and State/Branch filtering needed no changes.**
Confirmed by reading `ClinicalCaseManager::getClinicalCase()` directly: its `users` join CASE (`assigned_ccr` → `recruiting_schedule.ccm_id` → `mssql_patients.ccm_id`) and its facility resolution (`mssql_facilities` via `mssql_patients.aoc_facility_id`) already apply uniformly across both shift types with no coverage-specific branch — the existing `joinResolvedAssignee()`/`applyFilters()` in `CCRCalendarReadRepository` were already correct for both.

**`getWeekEvents()` request validated via a Form Request, not manual `isset()` parsing.**
Per code review, `CCRCoverageCalendarController::getWeekEvents(Request $request)`'s manual `isset($reqData['date'])`/`array_filter()` parsing was replaced with `App\Http\Requests\CCRCalendar\GetCoverageCalendarWeekEventsRequest` (extends the existing `CoreRequest` base, same convention as `ClientScheduleDropdownRequest`/`NeedToHireScheduleByClientIdRequest`). It validates `date` as a required date, `state`/`branch` as nullable strings, and `assignee`/`assignee.*` as a nullable array of integers, and exposes `toFilterDTO(PrcShiftType $shiftType): PrcCalendarFilterDTO` — mirroring the `toDTO()` helper pattern already used elsewhere — so the controller just calls `$request->toFilterDTO(PrcShiftType::Coverage)` instead of manually assembling the DTO from loose array reads. One intentional behavior change: a request missing `date` (which the calendar's own JS never sends, but could occur from a malformed/manual call) now gets a proper 422 validation response instead of silently rendering an empty calendar — a correctness improvement, not a regression, since no legitimate caller omits `date`.

**New sibling controller/view, not a shared parameterized route.**
No calendar family in this codebase (IPEA, TrachVent, After Hours, CCR, Intake) shares one controller/route/Blade across variants via a route parameter — each has its own controller and full route block. Following that established convention: `CCRCoverageCalendarController` (own `index`/`getWeekEvents`) and `resources/views/ccrcoverage/calendar.blade.php`, both closely modeled on the Recruiting equivalents but reusing the shared repository/`UserReadRepository` underneath. `resources/views/ccr/weekEvents.blade.php` is reused completely unmodified by both calendars — it was already shift-type-agnostic.

**Session key for "last viewed date" is calendar-specific (`lastCoverageCalendarSearch`), not shared.**
The Recruiting calendar's `getWeekEvents()` writes `Session::put(['lastCalendarSearch' => ...])`. Reusing that same key for the Coverage calendar would cause the two calendars' "last viewed date" to stomp on each other when a user switches between them in the same session. The Coverage calendar uses its own `lastCoverageCalendarSearch` key instead.

**Event-details modal extended with a Coverage branch, not duplicated.**
`resources/views/ccr/eventDetails.blade.php` already branches on `type_id == 996` (block-time) vs. the tracker-based default — a precedent for type-conditional rendering in this exact file. Added an `@elseif(!empty($schedule->coverage_id))` branch showing Coverage-relevant fields (clinician name, coverage shift date/time) instead of "Proposed Next Step"/Recruiter-Tracker-only fields, which would be blank/nonsensical for a `tracker_id`-less Coverage row. `CCRCalendarController::getEventDetails()` gained an additive `coverage_tracker` join/fields (existing tracker-based fields untouched) and its own `mssql_patients` join was corrected to `recruiting_schedule.aoc_patient_id` for the same reason as the repository fix, so "Client" resolves for Coverage rows too.

The "Clinician Name" field initially selected the raw `coverage_tracker.new_clinician_name` column directly — this was wrong: that column is only populated when the coverage shift is covered by a not-yet-onboarded clinician with no provider record; when it's covered by an existing provider, the correct name is `mssql_providers.fullName`, exactly the distinction `CCRCalendarReadRepository::candidateSelect()`'s `CASE` already makes for the calendar's own event title. Selecting the raw column caused the popup's "Clinician Name" to be blank whenever the calendar correctly showed a provider's name. Fixed by making `candidateSelect()` `public` and reusing it (`$this->ccrCalendarReadRepository->candidateSelect()`) for the popup's name field too, instead of a second, incomplete ad-hoc query — guaranteeing the popup and the calendar can never disagree about whose name to show.

The `extraHeader` icons ("Document Task" / "View Tracker Details") were initially just suppressed for Coverage rows since `openRecruiterDetails(tracker_id)` is broken when `tracker_id` is null. Per follow-up feedback, this was corrected to mirror existing behavior instead of hiding functionality: the CCM "Patient Review Calls" bucket (`CCRController::getClinicalCase()`, `resources/views/ccr/grid.blade.php`) already branches these exact two buttons on `coverage_id`, behind the `coverage-tracker-view-action` LD flag — Coverage rows call `openCCRSNSForm(id, 'coverage')` and `getDetailsOfCoverageTracker(coverage_id)` (opens the Coverage Tracker record) instead of `openCCRSNSForm(id)`/`openRecruiterDetails(tracker_id)`. Both JS functions already exist globally (`layouts/myaccount.blade.php`, `layouts/globalScript.blade.php`), included by the same `layouts.myaccount` layout both PRC calendars use, so this required no new JS — just replicating the same `@if(coverage_id) ... @else ... @endif` branch already proven in the bucket.

The Coverage calendar's own route `ccrCoverageCalendar.getEventDetails` points at the *same* `CCRCalendarController::getEventDetails` method (Laravel supports multiple route names → one action), avoiding a duplicate implementation.

**Both calendars gated by the existing `CCR Calendar` permission — no new permission group.**
An initial implementation added a separate `PRC Calendar – Coverage` permission group (its own `route`/`related` entry) so the new calendar could be independently granted. Per explicit direction, this was replaced: the three `ccrCoverageCalendar.*` route names were added to the existing `CCR Calendar` → `View Calendar` entry's `related` array instead, so a single permission grant controls both calendars. This is safe because `H::canPermissions()` (consumed by both the `@canPermission` Blade directive and the `AdminRole` route middleware) treats every route listed under `related` as equally granted to the entry's primary `route` — confirmed by reading `ProcessPermissions` (which syncs `related` into the `permissions` table's `related_routes` column) and `canPermissions()` itself (which merges `route_name` + `related_routes` before checking route membership). This is the same mechanism the existing `CCR Calendar` entry already uses to bundle `ccrCalendar.getWeekEvents`/`getEventDetails`/`addEvent`/`saveEvent` under one grantable permission — extending it to also cover the Coverage calendar's routes is consistent with that established pattern, not a new one.

## Risks / Trade-offs

- [Patient-join/candidate-CASE change also affects the already-shipped Recruiting calendar] → Low risk since it converges on logic already proven correct by the CCM dashboard bucket, but flagged for manual regression verification (candidate/client name, branch, assignee badge should render identically to before on the Recruiting calendar after this change).
- [Two calendars sharing one repository could still drift if a future change is made to only one call site] → Mitigated by the fact that both call the same two public methods with only the shift-type argument differing; any future filter/assignee logic change automatically applies to both.
- [Coverage calendar's event-details modal is a shared file with new conditional branches] → A future edit to the Recruiting-only tracker branch could accidentally affect Coverage's branch if someone edits the wrong `@elseif`; mitigated by keeping the three branches (`996`, coverage, default) clearly separated and independently readable.
- [`config/permissions.php`'s `related` change has no effect until synced] → The `permissions` DB table (not the config file) is what `H::canPermissions()` actually reads at runtime, and lookups are cached forever; deploying this change without running `php artisan process:permissions` (and flushing the `{permissions_cache}`/`{roles_permissions_cache}`/`{user_permissions_cache}` cache tags) would leave the Coverage calendar's routes ungated by the intended permission until that sync happens — flagged explicitly in `tasks.md` as a required post-deploy step, not an automatic side effect of merging code.

## Migration Plan

No data migration. Standard code release: new controller/routes/view/permission/nav-entry, plus additive/converging changes to already-shipped Recruiting-calendar files (repository, `getEventDetails`, `eventDetails.blade.php`). No feature flag. Rollback is a standard revert.
